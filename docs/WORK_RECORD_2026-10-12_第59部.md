## 1. FIM（ファイル整合性監視）の有効化

- 症状: `/tmp` に SUID ファイルを置いても検知されず、`kizuna-security-suid-fast.json` が `{}`。
- 原因: `kizuna-eye-agent.service` の **`PrivateTmp=yes`** により、エージェントが見る `/tmp` は隔離された `systemd-private-…/tmp`。攻撃者が置く実 `/tmp` のファイルが見えず、SUID / FIM 監視が原理的に無効化されていた（A-4 専用ユーザー化の副作用・サイレント故障）。
- 修正: `PrivateTmp=yes` → **`no`**（`/usr/lib/systemd/system/kizuna-eye-agent.service` とリポジトリ `systemd/kizuna-eye-agent.service`）。`ProtectSystem=strict` + `ReadWritePaths` は維持（書き込み権限は増えない）。
- 検証: 新規 SUID ファイルを **CRITICAL** で検知。

### FIM の有効化（fim_watch）
- `modules.json` の `fim_watch: false` → **`true`**、`fim_watch_ignore` を設定。
- `fim_watch_max_size_kb`: 4096 → **16384**（16MB）。
- 残っていた「大きすぎて除外」114件は、過去セッションの開発残骸（`/tmp/*.so`, `kz-backup-*` 等）。**ビルド残骸を削除**、`/tmp/kz-backup-*` 等の静的バックアップは `fim_watch_ignore` に追加（`kz-backup-*,old-plugins-backup,kzsec-migrate-*`）。
- 検証: `/tmp` にファイルを作成・変更・削除 → 作成/変更 **CRITICAL**、削除 WARNING を検知。
- 気づき: ignore パターンに一致するファイルの新規作成は **INFO で記録**（ignore を悪用した検知すり抜けの可視化）。

## 2. ログのリモート転送（🟡-3-A）の有効化

- 目的: agent ユーザーが奪取されても、転送済みログ（別プロセス）が残るようにする。
- 実装は `pkg/logger/forward.go` に存在済み（`cmd/agent/main.go:174` で配線済み）。**設定だけで有効化**できる。
- 同一マシン（サブ鯖）に簡易 NDJSON コレクタを新設:
  - `/usr/lib/kizuna-eye/kizuna-log-collector.py`（Python stdlib、NDJSON を追記保存）
  - `kizuna-log-collector.service`（User=kizuna-eye、127.0.0.1:9200、`/var/lib/kizuna-eye-logs-forward/`）
- `agent_config.json` に `log_forward: {url: http://127.0.0.1:9200, timeout_sec: 5}` を追加。
- 検証: `forward-20261012.ndjson` に agent ログが転送されることを確認。
- 制約: 同一マシンなので root 奪取時は無効。メイン鯖が戻ったら **`log_forward.url` を別マシン IP に変更**して本命化。

## 3. 🟡-5 Step A: 特権ヘルパーの socket activation 化

### 背景
- ワンクリック対処は dashboard が `sudo -n /usr/local/bin/kizuna-action.sh` を呼ぶ方式。
- この方式だと dashboard unit に `NoNewPrivileges`/`ProtectSystem=strict` を付けられない（sudo が no-new-privs 下で失敗）。
- apt パッケージング的にも sudoers 生成は壊れやすく避けたい。

### 設計（socket activation）
- dashboard（非特権）→ Unix ソケット `/run/kizuna-eye/action.sock` → `kizuna-action.service`（root、最小ケーパビリティ）→ 既存 `kizuna-action.sh`。
- ソケットは `root:kizuna-eye 0660`。接続元は `SO_PEERCRED` で検証。
- JSON Lines プロトコル: `{"action":"kill_port","args":["44444"]}` → `{"ok":true,"detail":"..."}`。

### 実装（Step A = サーバー側のみ。dashboard は未変更）
| ファイル | 配置 |
|---|---|
| `kizuna-action.sh` | `/usr/lib/kizuna-eye/`（root:root 755） |
| `kizuna-action-server`（Python） | `/usr/lib/kizuna-eye/`（root:root 755） |
| `kizuna-action.socket` | `/lib/systemd/system/`（active） |
| `kizuna-action.service` | `/lib/systemd/system/`（socket activation, root, CAP_KILL/CAP_NET_ADMIN/CAP_DAC_OVERRIDE） |
| `kizuna-eye.conf`（tmpfiles.d） | `/usr/lib/tmpfiles.d/`（/run/kizuna-eye 保証） |

### 検証（すべて合格）
- valid `kill_port 44444`（未使用）→ `{"ok":false,"error":"no process is listening on port 44444"}`（ヘルパー動作）
- valid `unblock_ip 198.51.100.7` → `{"ok":true}`
- invalid action `rm_rf` → `{"ok":false,"error":"unsupported action"}`
- invalid arg `abc; rm -rf /` → `{"ok":false,"error":"argument contains forbidden characters"}`
- 接続元検証: kizuna-eye ユーザーのみ接続可。

## 教訓
- systemd の `PrivateTmp=yes` は共有 `/tmp` を監視する機能（SUID/FIM/ポート）と両立しない。監視ツールの agent では原則 `no`。
- 「設定は正しいのに検知ゼロ」は、コードでなく実行環境（namespace/隔離）を疑う。
- sudoers を使わず socket activation にすると、apt パッケージングがきれいになり、dashboard を strict 化できる。
